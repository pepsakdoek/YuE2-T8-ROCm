# Running the upstream example song on RDNA2 (RX 6800 / gfx1030)

This is the concrete record of getting the kit to run the **original repository's**
example song — `examples/song.json`, id `city_lights` — on a Radeon RX 6800 under
native Windows ROCm. The kit itself was validated on an RX 9070 XT (gfx1201 /
RDNA4); this documents what changes for RDNA2.

## Result

```
outputs/city_lights/audio.flac   48 kHz stereo PCM_24, 66.679 s
peak 0.709   rms 0.103   dc +2.2e-05   all samples finite, no clipping
truncated: {abc: false, semantic: false}
e2e 890.2 s (14.8 min)   ratio 13.35 s per audio second
```

Ten artifacts, all re-hashed against `result.json` by
`scripts/rocm/verify_example_song.py`. The generated plan is real music notation
— `score.abc` carries chord symbols (`C`, `Em`, `Fmaj7`, `Am7`, `Fsus4`, `G`)
across the `Vocal` and `Ins` voices, with the example lyrics' intro/verse/chorus
structure.

| stage | RX 6800 (gfx1030) | RX 9070 XT (gfx1201, kit's own numbers) |
|---|---:|---:|
| score planning | 131.9 s (5.05 tok/s, 666 tok) | 24.4 s (22.1 tok/s, 540 tok) |
| semantic tokens | 324.9 s (5.13 tok/s, 1668 tok) | 60.7 s (24.7 tok/s, 1500 tok) |
| NAR flow matching | 106.3 s | 5.9 s |
| VAE decode | 265.1 s / 4 chunks | 165.8 s / 3 chunks |
| **e2e** | **890.2 s** | **267.9 s** |

Roughly **3.3x slower** overall, concentrated in the two autoregressive stages
(~4.5x), which is the expected cost of RDNA2 having no hardware BF16.

## The one real blocker: RDNA2 has no torch wheels in the v2 tree

`rocm.nightlies.amd.com/v2/gfx103X-*` publishes the ROCm runtime libraries but
**no `torch`, `torchaudio` or `torchvision`** — every other family
(`gfx110X-all`, `gfx120X-all`, `gfx1151`, `gfx94X-dcgpu`, …) has them. Since the
kit's `setup_rocm_runtime.ps1` hardcoded `v2/gfx120X-all/` for torch, the
documented install path cannot work on an RX 6800.

AMD does build RDNA2 torch wheels, under the **staging** index, which is also
what the Wan2GP Windows/AMD guide documents for `gfx103X-dgpu`:

```
https://rocm.nightlies.amd.com/v2-staging/gfx103X-dgpu/
```

Verified there for `cp312` + `win_amd64`:
`torch 2.11.0+rocm7.13.0a20260421`, `torchaudio 2.11.0a0+rocm7.13.0a20260421`.

Two further differences from the RDNA4 path:

* the `rocm` sdist on those indexes publishes no `rocm-sdk-device-<isa>`
  package, so the `device-<isa>` extra fails; use `rocm[libraries,devel]`;
* torchaudio's build string is not the same as torch's (`2.11.0a0+…` vs
  `2.11.0+…`), so they need separate pins.

`scripts/rocm/setup_rocm_runtime.ps1` now takes `-FamilyIndex`,
`-TorchAudioVersion`, `-RocmExtra` and `-RocmFromFamilyIndex` to cover this
without disturbing the RDNA4 defaults.

## Commands

```powershell
# 1) ROCm runtime for RDNA2 (embedded CPython 3.12 + AMD TheRock staging wheels)
powershell -ExecutionPolicy Bypass -File scripts\rocm\setup_rocm_runtime.ps1 `
    -Device gfx103X-dgpu `
    -TorchVersion '2.11.0+rocm7.13.0a20260421' `
    -TorchAudioVersion '2.11.0a0+rocm7.13.0a20260421' `
    -FamilyIndex 'https://rocm.nightlies.amd.com/v2-staging/gfx103X-dgpu/' `
    -RocmExtra 'libraries,devel' -RocmFromFamilyIndex `
    -SkipRequirements -SkipPlaywright

# 2) the yue2 dependency set (the T8 app's full lock is not needed for the CLI route)
runtime\python.exe -m uv pip install --python runtime\python.exe --system --link-mode copy `
    transformers==4.57.6 huggingface-hub==0.36.2 safetensors==0.7.0 tiktoken==0.12.0 `
    numpy==2.2.6 soundfile==0.13.1 accelerate==1.13.0

# 3) upstream example + official weights
git clone --depth 1 https://github.com/multimodal-art-projection/YuE YuE
powershell -ExecutionPolicy Bypass -File scripts\rocm\fetch_example_models.ps1

# 4) sanity-check the GPU kernels before committing to a long run
runtime\python.exe scripts\rocm\check_gfx1030_gpu.py

# 5) run the example song
runtime\python.exe scripts\rocm\run_example_song.py --output outputs\city_lights

# 6) verify
runtime\python.exe scripts\rocm\verify_example_song.py outputs\city_lights
```

`models/YuE2-3B/model.safetensors` and `models/YuE2-Vae/model.safetensors`
downloaded from `m-a-p` are byte-identical to the hashes this repository pins
(`1d55c42c…a59e9`, `807ce9d5…7751346`), so the t8 manifest contract is intact.

## Does BF16 actually work without BF16 hardware?

`torch.cuda.is_bf16_supported()` returns `True` for **any** HIP build, so the
pipeline's BF16 gate proves nothing on gfx1030. `scripts/rocm/check_gfx1030_gpu.py`
therefore checks the operations the generation path uses and compares each
against a float32 reference:

| operation | result |
|---|---|
| bf16 matmul 2048x2048 | `rel_err 2.238e-03` (normal bf16 rounding) |
| bf16 linear head | `rel_err 2.802e-03` |
| bf16 SDPA, and masked SDPA | finite |
| fp32 conv1d (the VAE path) | finite |

BF16 is emulated by upconverting, which is where the slowdown comes from — but
it computes correctly.

## Benign warnings seen on gfx1030

* `Attempting to use hipBLASLt on an unsupported architecture! Overriding blas
  backend to hipblas` — RDNA2 has no hipBLASLt. Do **not** set
  `TORCH_BLAS_PREFER_HIPBLASLT=1` on this card; it is simply ignored.
* `1Torch was not compiled with memory efficient attention` — SDPA falls back to
  the math backend. This is the same masked-SDPA path the ROCm patch forces
  deliberately, so it is not a regression.
* `CK grouped conv library not found for device gfx1030` — MIOpen lacks the CK
  solver for RDNA2 and uses another one.
* `Solver <GemmFwdRest>, workspace required: …, provided ptr: 0 size: 0` — the
  same benign workspace notices the kit already documents.
* `xnack 'Off' was requested for a processor that does not support it!` — gfx1030
  has no XNACK.

## Notes

* The first bf16 GEMM (39.7 s) and the first conv1d (12.2 s) include one-off
  Tensile/MIOpen solver tuning. Do not read those as steady-state costs; they are
  cached afterwards.
* `--backend torch-eager` is kept for the RDNA2 run for the same reasons as on
  RDNA4 (faster at production sequence lengths, and it exits 0). The CUDA-graph
  path's `seqused_k` blocker is a ROCm-wide issue, not RDNA2-specific.
* The song came out 66.7 s where the kit measured 59.96–63.68 s for the same
  `city_lights` request. Both are complete, untruncated renders of the same
  two-section lyric; the length difference is downstream of a different torch
  build and does not indicate a failure. Worth a same-session A/B before
  quoting either number.
